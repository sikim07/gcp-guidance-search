# Claude Code 구현 프롬프트

Claude Code 새 세션에 **단계 하나를 그대로 붙여 넣기** 위한 원문이다. 이 저장소에는 0~6단계가 이미 구현되어 있다. 재구현·확장 세션에서만 사용한다.

사용법:

1. 세션을 연다.
2. 아래 표에서 해당 단계의 코드 블록만 복사한다.
3. 한 세션에 여러 단계를 넣지 않는다. 0단계 → 확인 → 0-1 → 1… 순서.

| 단계 | 목적 | 이 저장소 상태 |
| --- | --- | --- |
| 0 | 개요·아키텍처 (코드 금지) | 설계 확정 후 구현 완료 |
| 0-1 | Stop 훅 | `.claude/hooks/stop-review.mjs` |
| 1 | 수집 파이프라인 | `lib/pipeline/sources/*` |
| 2 | 청크·임베딩·벤치마크 | `BENCHMARK.md` |
| 3 | 검색 API | `POST /api/search` |
| 4 | 챗 UI + 피드백 | `/`, Playwright |
| 5 | 개정 감지 (핵심) | Cron + `change_log` |
| 6 | 배포·실사용 준비 | README, `/admin` |

확정 사항 (프롬프트를 붙여 넣을 때도 바꾸지 말 것):

- 우선순위: 개정 감지 파이프라인 > 검색/답변 품질 > UI
- 벡터DB 없음. 청크 5,000 또는 유사도 계산 500ms 초과 시에만 pgvector 검토
- KGCP = 「의약품 등의 안전에 관한 규칙」 **별표 4** (별표 1 GMP 아님)
- 식약처 m_1060는 임상시험 관련 안내서만
- v1 OCR 없음

## 0단계 — 전체 개요 (세션 시작 시 1회)

```
"GCP 가이드라인 검색기"라는 사이드 프로젝트를 처음부터 구축한다.

## 프로젝트 본질
이 프로젝트의 핵심은 "검색 기능"이 아니라 "여러 규제 사이트(FDA, 식약처)에 흩어진
임상시험 가이드라인 문서의 개정을 자동으로 감지하고 반영하는 파이프라인"이다.
검색/챗 UI는 그 결과를 자연어로 조회하는 인터페이스일 뿐이다.
이 우선순위를 항상 기억할 것: 개정 감지 파이프라인 > 검색/답변 품질 > UI.

## 대상 사용자
- 나 자신 (EDC 프론트엔드 개발자, 임상시험 실무자는 아님)
- 외부 실사용자 (CRA, RA 등 임상시험 주변 실무자) — 커뮤니티 배포 예정

## 데이터 소스 (전부 공개, 저작권 문제 없음)
- FDA가 미러링한 ICH 가이드라인: https://www.fda.gov/science-research/clinical-trials-and-human-subject-protection/ich-guidance-documents
- FDA 자체 가이던스: https://www.fda.gov/science-research/clinical-trials-and-human-subject-protection/clinical-trials-guidance-documents
- 식약처(MFDS) 민원인안내서 게시판: https://www.mfds.go.kr/brd/m_1060/list.do
- 국가법령정보센터의 임상시험 관리기준(KGCP): https://www.law.go.kr
  ※ KGCP는 「의약품 등의 안전에 관한 규칙」 별표 4이다. 별표 1(GMP)이 아니다.

## 기술 스택 및 핵심 의사결정 (임의로 바꾸지 말 것)
- FE+BE: Next.js (API Routes 포함), TypeScript strict mode 필수
- 배포: Vercel
- DB: Supabase(Postgres) — 문서 메타데이터, 청크, 임베딩, 버전 이력, 검색 로그, 피드백 저장
- 임베딩: OpenAI text-embedding-3-small
- 답변 생성: Claude API (Haiku 계열, 비용 우선)
- **벡터DB는 쓰지 않는다.** 이유: 현재 예상 청크 수(수백 개)에서는 브루트포스 코사인
  유사도 계산으로 충분함을 벤치마크로 증명할 것 (2단계 프롬프트에서 진행).
  청크 수가 5,000개를 넘거나 검색 응답시간이 500ms를 초과하면 pgvector 전환을
  고려한다는 조건을 코드 주석과 README에 명시할 것.
- 코드 품질: ESLint + Prettier, 테스트는 Vitest(BE 로직), Playwright(FE 핵심 흐름)
- Claude Code Stop 훅: 구현이 끝날 때마다 다른 모델(GPT 또는 Gemini API)에게
  git diff를 보내 자동 코드 리뷰를 요청하고, 문제 발견 시 종료를 막는 구조를
  프로젝트 초기에 반드시 세팅한다 (아래 0-1 프롬프트 참고).

## 비용 통제 원칙
- IP당/전체 일일 요청 한도를 코드 레벨에서 강제
- API 제공사의 월 지출 한도 설정 활용
- 반복 질문 캐싱

먼저 프로젝트 폴더 구조와 전체 아키텍처 설계안을 제시하고, 내 확인을 받은 후 진행해줘.
아직 코드는 작성하지 말 것.
```

## 0-1단계 — Claude Code Stop 훅

```
프로젝트 루트에 .claude/settings.json을 만들고 Stop 훅을 등록해줘.

요구사항:
- 매번 응답을 마치기 전에, 이번 세션에서 변경된 파일들의 git diff를 추출하는 스크립트를 실행
- 그 diff를 [GPT-4 또는 Gemini API 중 내가 지정할 것]에 보내서
  "이 코드 변경사항에 버그, 타입 불일치, 놓친 엣지케이스가 있는지 검토해줘"라는
  고정 프롬프트로 리뷰 요청
- 리뷰 응답에 심각한 문제가 있다고 판단되면 { "decision": "block", "reason": "..." }를
  반환해서 내(Claude Code)가 계속 수정하도록 강제
- 문제가 없으면 그냥 통과
- 리뷰 결과는 항상 로그 파일(예: .claude/review-log.jsonl)에 누적 기록

스크립트 언어는 Node.js로 작성하고, API 키는 환경변수로 관리해줘.
리뷰 제공자는 환경변수 STOP_REVIEW_PROVIDER=gemini|openai 로 고른다. 기본은 Gemini.
API 키가 없으면 로컬 개발이 멈추지 않게 통과하고 로그만 남긴다.
무한 루프 방지: 같은 diff를 3회 block 하면 그다음엔 통과.

먼저 훅 스크립트 설계안을 보여주고 확인받은 후 구현해줘.
```

## 1단계 — 문서 수집 파이프라인

```
1단계: 문서 수집 파이프라인을 구현한다.

요구사항:
- 위에서 지정한 4개 소스 URL을 정기적으로 fetch해서 문서 목록(제목, URL, 발행일/고시일,
  카테고리)을 파싱하는 스크래퍼 작성
- 각 사이트마다 HTML 구조가 다르므로 소스별로 파서를 분리 (fda-parser.ts,
  mfds-parser.ts, kgcp-parser.ts)
- 새로 발견된 문서는 PDF를 다운로드하고, 파일의 SHA-256 해시값을 계산해 저장
- Supabase에 documents 테이블 설계: id, source, title, url, issued_date,
  file_hash, current_version_id, created_at
- 이번 단계에서는 크롤링/저장까지만 구현하고, 임베딩은 다음 단계에서 진행
- 유닛 테스트: 각 파서가 실제 HTML 샘플(테스트 픽스처로 저장)에서 올바르게
  파싱하는지 검증
- 식약처 m_1060는 임상시험 관련 안내서만 수집 (게시판 전체 금지)
- KGCP는 별표 4만

우선 6개 문서(E6(R2), Electronic Systems/Records/Signatures Q&A, Electronic Source
Data, Part 11 Scope and Application, Risk-Based Approach to Monitoring, Informed
Consent)와 식약처 KGCP 관련 문서로 시작해줘.
```

## 2단계 — 청크·임베딩 + 벡터DB 벤치마크

```
2단계: 문서 청킹과 임베딩, 그리고 벡터DB 필요성 벤치마크를 진행한다.

요구사항:
- PDF에서 텍스트를 추출하고, 조항/섹션 번호를 기준으로 청크 분할 (문단이 아니라
  조항 단위로 자르는 게 우선순위 — 문맥 손실 최소화)
- 각 청크를 OpenAI text-embedding-3-small로 임베딩, Supabase에 청크 텍스트+임베딩
  벡터(JSON 컬럼)로 저장. pgvector 컬럼을 만들지 말 것.
- 벤치마크 스크립트 작성: 청크 수를 100 / 1,000 / 10,000 / 100,000개로 늘려가며
  (뒤쪽은 테스트용 더미 데이터로 복제 생성) 브루트포스 코사인 유사도 계산 시간을
  측정하고, 같은 데이터로 pgvector(HNSW 인덱스) 검색 시간과 비교
- 벤치마크 결과를 표/그래프로 정리한 마크다운 리포트 생성 (BENCHMARK.md)
- 현재 실제 청크 수를 이 그래프 위에 표시해서, 브루트포스로 충분한 근거를 시각화
- 이 벤치마크 결과에 따라 브루트포스 유사도 계산 함수를 구현 (벡터DB 없이)
- 코드 주석과 README에 전환 조건을 명시: 청크 5,000개 초과 또는 유사도 계산 500ms 초과
```

## 3단계 — 검색 + LLM 답변 생성

```
3단계: 검색과 답변 생성 API를 구현한다.

요구사항:
- POST /api/search: 사용자 질문을 임베딩 → 브루트포스 유사도 계산으로 상위 N개
  청크 추출 → Claude API에 청크와 질문을 전달해 답변 생성
- 프롬프트 설계 시 반드시 포함: (1) 제공된 청크 내용에만 근거해 답변할 것,
  모르면 모른다고 할 것 (환각 방지), (2) 답변의 각 문장에 출처(문서명, 조항 번호)를
  함께 표기할 것
- 응답 스키마: { answer: string, sources: [{ title, section, url }] }
- 요청 한도(rate limit)를 이 API에 바로 적용: IP당 하루 20건, 전체 하루 200건
  (환경변수로 조정 가능하게)
- 캐싱: 동일하거나 유사도가 매우 높은 질문은 캐시된 답변 재사용 (Supabase에
  query_cache 테이블)
- 테스트: 프롬프트 인젝션 시도, 관련 문서가 없는 질문에 대한 처리 등 엣지케이스 포함
```

## 4단계 — 챗 UI + 피드백

```
4단계: 프론트엔드 챗 UI를 구현한다.

요구사항:
- Next.js 페이지: 질문 입력창, 답변 표시(출처 링크 포함), 로딩 상태
- 각 답변 아래 👍/👎 피드백 버튼 → 클릭 시 Supabase feedback 테이블에
  { query, answer, rating, timestamp } 저장
- 반응형 디자인, 최소한의 깔끔한 UI (frontend-design 원칙 참고)
- Playwright E2E 테스트: 질문 입력 → 답변 표시 → 피드백 클릭까지의 전체 흐름
- 개정 피드(/updates)를 검색과 동등한 1등 화면으로 둘 것. 파이프라인이 본체다.
```

## 5단계 — 개정 자동 감지 파이프라인

```
5단계: 개정 자동 감지 파이프라인을 구현한다. 이게 이 프로젝트의 핵심 파트다.

요구사항:
- 신규 문서 감지: 1단계에서 만든 스크래퍼를 재실행해 목록을 다시 가져오고,
  기존 documents 테이블과 비교해 새 URL/제목을 찾아냄
- 기존 문서 개정 감지:
  1차: 사이트가 제공하는 날짜(FDA Date Issued, 식약처 고시일)가 저장된 값보다
       최신이면 개정으로 판단
  2차: 재다운로드한 PDF의 SHA-256 해시가 기존과 다르면 (날짜 표기가 그대로여도)
       개정으로 판단
- 개정 감지 시: 새 텍스트와 이전 텍스트를 문단 단위로 diff (difflib 방식) →
  바뀐 조항만 재청크·재임베딩 (전체 재처리 금지, 비용 절감이 목적)
- 버전 관리: document_versions 테이블에 이전 버전을 보존, current_version_id를
  새 버전으로 갱신, 변경 로그를 change_log 테이블에 기록
- 실행 방식: Vercel Cron Job으로 매일 1회 자동 실행
- 감지 결과를 관리자(본인)에게 알림 (이메일 또는 Slack webhook)
- 테스트: 날짜만 바뀐 경우 / 내용만 바뀐 경우 / 둘 다 안 바뀐 경우를 각각
  시뮬레이션한 통합 테스트
```

## 6단계 — 배포 및 실사용 준비

```
6단계: 배포하고 실사용 시작을 준비한다.

요구사항:
- Vercel에 배포, 환경변수(API 키, Supabase 연결정보) 설정
- README.md 작성: 프로젝트 소개, 아키텍처 다이어그램(mermaid), 로컬 실행 방법,
  기술적 의사결정 근거(벡터DB 미사용 이유 + 벤치마크 링크 포함)
- 검색 로그/피드백을 확인할 수 있는 간단한 관리자 조회 스크립트 또는 페이지
  (화려한 대시보드 불필요, 본인만 보는 용도)
- 배포 후 본인이 실제 업무 중 2~3주간 사용하며 로그를 남길 수 있는 상태인지 최종 점검
- OpenAI/Anthropic 콘솔의 월 지출 한도를 README 체크리스트에 명시
```
